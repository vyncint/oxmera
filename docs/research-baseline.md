# Research baseline — toolchain reconnaissance (stage O3)

Measured 2026-08-21 on `aarch64-apple-darwin` (Apple Silicon), no CUDA
toolkit, no GPU. Every number below comes from the re-runnable command
shown with it. Numbers are per-machine and per-toolchain; re-measure after
any pin bump — do not edit this file, replace it.

Toolchain under measurement: `nightly-2026-04-03`, reconverge **0.2.0**
(`cargo-reconverge` + `reconverge-driver`), cuda-oxide **`a766fc26`**,
launchbound **1.0.2**.

## (a) Fresh-clone check time, stable root workspace

```
$ git clone https://github.com/vyncint/oxmera && cd oxmera
$ /usr/bin/time -p cargo check --workspace --all-targets
real 4.88   user 2.16   sys 0.89
```

4.9 s on a warm cargo registry. The workspace is nine skeleton crates plus
`thiserror`; treat this as the floor, not a property.

## (b) `cargo reconverge check --strict` on an exercise kernel (tier 0)

Kernel: `exercises/b1-first-kernel` (elementwise skeleton, cuda-device
`a766fc26` as a git dependency, pinned nightly via the exercise's
`rust-toolchain.toml`).

```
$ cd exercises/b1-first-kernel
$ cargo clean && /usr/bin/time -p cargo reconverge check --strict   # cold
reconverge: 0 deny, 0 confirmed, 0 warning finding(s)
real 3.63
$ /usr/bin/time -p cargo reconverge check --strict                  # warm
real 0.08
```

Cold ≈ 3.6 s (dominated by checking cuda-device), warm ≈ 0.08 s. The
correctness gate is effectively free once the graph is built — run it on
every kernel edit without thinking about it.

## (c) `cargo oxide inspect` in the tier-1 container

Container: Apple `container` tool, native arm64 Ubuntu 24.04 guest,
provisioned imperatively (no Docker, no Rosetta) with CUDA toolkit 13.2
(sbsa), LLVM 21, the pinned nightly, and cargo-oxide 0.2.1.

```
$ container exec cuda-oxide-dev bash -lc 'cd /work && time cargo oxide inspect vecadd'
...
        add.f32         %r10, %r8, %r9;
        st.global.b32   [%rd4], %r10;
...
real    0m9.355s
```

Real PTX from Rust source, 9.4 s warm, $0, no GPU. Two findings worth
keeping:

- A `#[kernel]` whose body is `todo!()` **builds but emits no PTX** —
  `cargo oxide inspect` reports "could not read generated PTX". So the
  exercise skeletons compile and pass the convergence gate, but the
  inspect step only opens once a real body exists. The gate gates the
  solution, not the skeleton, which is the right way around.
- The arm64-container PTX path was previously verified byte-identical to
  the x86_64 box for a sample kernel; that check must be repeated at
  exercise D1 before any container PTX is treated as box-equivalent.

## (d) launchbound 1.0.2 driving reconverge 0.2.0 — the §pin pairing

This pairing is newer than the one launchbound pins internally
(reconverge 0.1.11); it had never been measured together before this.

Clean space (this repo's B1 skeleton, 3 configs):

```
$ cd exercises/b1-first-kernel && launchbound prune --cc 7.5 .
b1-first-kernel (cc 7.5):
  => 3 clean, 0 with caveats, 0 refused, 0 tool errors
real 3.21
```

Refusal flow (the known-flip corpus kernel from
`vyncint/launchbound-action-demo`, 4 configs, cc 8.6):

```
block_x=32 tile=128 -> clean []
block_x=32 tile=256 -> clean []
block_x=64 tile=128 -> disqualified ['RC001']
block_x=64 tile=256 -> disqualified ['RC001']
```

Exactly the expected verdicts, in both directions: clean configs admitted,
the multi-warp flip refused with RC001 through the `findings.v1` schema.
**Verdict: launchbound 1.0.2 drives reconverge 0.2.0 correctly.** The
documented fallback (pin reconverge 0.1.11) is not needed.

## Non-transfer reminders

A verdict is per-`--cc` (RC004 shared-memory context differs between 7.5
and 8.6) and timings are per-part. Nothing in this file predicts NVIDIA
performance; it measures tool latency on one laptop.
