# Research baseline — toolchain measurements

Re-measured 2026-08-26 on `aarch64-apple-darwin` (Apple Silicon), no CUDA
toolkit on the host, no GPU, after the pin bump reconverge 0.3.0→0.4.0 and
launchbound 1.2.0→2.0.0 (nightly and cuda-oxide unchanged — 0.4.0's own
`conformance/PIN` and `rust-toolchain.toml` still verify `a766fc26` on
`nightly-2026-04-03`; termlens stays 0.6.1). Every number comes from the
re-runnable command shown with it. Numbers are per-machine and
per-toolchain; re-measure after any pin bump — do not edit this file,
replace it. The 2026-08-22 baseline under reconverge 0.3.0 / launchbound
1.2.0 is in git history.

Toolchain under measurement: `nightly-2026-04-03`, reconverge **0.4.0**
(`cargo-reconverge` + `reconverge-driver`), cuda-oxide **`a766fc26`**,
launchbound **2.0.0** (action `@v2`, SHA-pinned), termlens **0.6.1**.

## (a) Fresh-clone check time, stable root workspace

```
$ git clone <repo> fresh && cd fresh
$ /usr/bin/time -p cargo check --workspace --all-targets
real 16.77   user 24.33   sys 4.74
```

16.8 s on a warm cargo registry. Up from 5.6 s: that baseline predates the
pivot — the workspace is now eleven crates of real framework code plus
their test targets. Still the floor, not a property.

## (b) `cargo reconverge check --strict` on the kernel crate

Kernel: `research/oxmera-cuda-oxide` (11 kernels: 8 elementwise, 2 reductions,
1 tiled GEMM; cuda-device `a766fc26`, pinned nightly via
`research/rust-toolchain.toml`).

```
$ cd research/oxmera-cuda-oxide
$ cargo clean && /usr/bin/time -p cargo reconverge check --strict --cc 8.6   # cold
reconverge: 0 deny, 0 confirmed, 0 warning findings
real 2.91
$ /usr/bin/time -p cargo reconverge check --strict --cc 8.6                  # warm
reconverge: 0 deny, 0 confirmed, 0 warning findings
real 0.07
$ cargo reconverge check --strict --cc 7.5
reconverge: 0 deny, 0 confirmed, 0 warning findings
```

Cold ≈ 2.9 s, warm ≈ 0.07 s — the gate is free after the first build.
(0.4.0 also changed the summary grammar: `findings`, not `finding(s)`.)

### RC004 acceptance — the #65 fix, measured here

The gap found on 2026-08-22 (named-const `SharedArray` sizes invisible to
RC004) is closed. With `TILE` temporarily set to 20480 (81920 B stage +
128 B partials):

```
$ cargo reconverge check --strict --cc 8.6
error[RC004]: kernel `reduce_sum` declares 82048 bytes of static shared memory, over the 49152-byte static limit
error[RC004]: kernel `reduce_max` declares 82048 bytes of static shared memory, over the 49152-byte static limit
reconverge: 2 deny, 0 confirmed, 0 warning findings
```

Under 0.3.0 this exact tree was `0 deny, 0 confirmed, 0 warning`.

## (c) PTX in the tier-1 container — both compute capabilities

Container: Apple `container` tool, native arm64 Ubuntu 24.04 guest, CUDA
toolkit 13.2 (sbsa), pinned nightly, cargo-oxide 0.2.1 — unchanged by this
bump. The crate is copied in (`tar | container exec -i … tar x`) and built
standalone.

```
$ cargo oxide inspect --arch sm_75      # Finished `release` in 7.29s; .target sm_75
$ ptxas -arch=sm_75 -v oxmera_cuda_oxide.ptx -o sm_75.cubin       # exit 0
$ cargo oxide inspect --arch sm_86      # Finished `release` in 7.30s; .target sm_86
$ ptxas -arch=sm_86 -v oxmera_cuda_oxide.ptx -o sm_86.cubin       # exit 0
ptxas info : reduce_sum   : Used 20 registers, used 1 barriers, 4224 bytes smem   (sm_86)
ptxas info : reduce_max   : Used 20 registers, used 1 barriers, 4224 bytes smem
ptxas info : matmul_tiled : Used 38 registers, used 1 barriers, 4096 bytes smem
ptxas info : vec_*        : 16–22 registers, 0 barriers
```

11 `.visible .entry` symbols; the static shared totals (4224 B = 1024×4 +
128; 4096 B = 2 buffers × 2 × 16×16 × 4) match `params.rs`. Instruction
census from the PTX: `reduce_*` 2 × `bar.sync` + 10 × `shfl.sync`,
`matmul_tiled` 2 × `bar.sync`, elementwise 0 barriers.

**Finding (this bump):** the first sm_75 build failed —
`CUDA target sm_75 cannot lower generated intrinsic ex2_approx_f32 …
requires sm_80 or newer`. Every float intrinsic in cuda-oxide's catalog at
`a766fc26` is `sm_80+`, while `kernel.toml` promised `needs_cc = "7.5"`
and `launchbound prune --cc 7.5` had admitted the whole space: the static
gate verifies convergence, not instruction availability. Fixed on our side
with plain-arithmetic `exp`/`tanh` (host-tested: `exp` worst relative
error 2.53e-7 against `f32::exp`, sigmoid/GELU within 1e-5 of `std`);
reported as vyncint/launchbound#32.

## (d) launchbound 2.0.0 driving reconverge 0.4.0 — the pin pairing

launchbound 2.0.0 pins reconverge 0.4.0 internally; the project's pairing
and launchbound's own are identical, as with 1.2.0/0.3.0.

```
$ cd research/oxmera-cuda-oxide
$ /usr/bin/time -p launchbound prune --cc 7.5 .
oxmera-cuda-oxide (cc 7.5):
  => 12 clean, 0 with caveats, 0 refused, 0 tool errors
real 3.21
$ /usr/bin/time -p launchbound prune --cc 8.6 .
oxmera-cuda-oxide (cc 8.6):
  => 12 clean, 0 with caveats, 0 refused, 0 tool errors
real 3.19
```

Refusal flow, on this crate, with `20480` temporarily added to
`dims.tile`:

```
$ launchbound prune --cc 7.5 .
  x c1-…  block_x=32  tile=20480   REFUSED RC004 at src/reduce.rs:37:5 … holds at every launch shape
  x c1-…  block_x=64  tile=20480   REFUSED RC004 …
  x c1-…  block_x=128 tile=20480   REFUSED RC004 …
  x c1-…  block_x=256 tile=20480   REFUSED RC004 …
  => 12 clean, 0 with caveats, 4 refused, 0 tool errors
```

**Verdict: launchbound 2.0.0 drives reconverge 0.4.0 correctly, and the
gate now refuses the over-cap named-const tile it admitted under 1.2.0;
no fallback needed.**

## Not measured

No kernel has executed on NVIDIA hardware. Runtime parity against the CPU
backend, timings, and the `needs_cc` claim itself remain tier-2 work:
metered sessions with evidence logs, not predictions. `ptxas` acceptance
is necessary for execution, not sufficient.

## Non-transfer reminders

A verdict is per-`--cc` and timings are per-part. Nothing in this file
predicts NVIDIA performance; it measures tool latency on one laptop and
assembler acceptance in one container.
