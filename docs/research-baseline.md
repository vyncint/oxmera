# Research baseline — toolchain measurements

Re-measured 2026-08-22 on `aarch64-apple-darwin` (Apple Silicon), no CUDA
toolkit, no GPU, after the pin bump reconverge 0.2.0→0.3.0, launchbound
1.0.2→1.2.0, termlens 0.5→0.6 (nightly and cuda-oxide unchanged — 0.3.0's
own toolchain file keeps `nightly-2026-04-03` verified against
`a766fc26`). Every number comes from the re-runnable command shown with
it. Numbers are per-machine and per-toolchain; re-measure after any pin
bump — do not edit this file, replace it. The 2026-08-21 baseline under
reconverge 0.2.0 / launchbound 1.0.2 is in git history.

Toolchain under measurement: `nightly-2026-04-03`, reconverge **0.3.0**
(`cargo-reconverge` + `reconverge-driver`), cuda-oxide **`a766fc26`**,
launchbound **1.2.0**, termlens **0.6.0**.

## (a) Fresh-clone check time, stable root workspace

```
$ git clone <repo> && cd oxmera
$ /usr/bin/time -p cargo check --workspace --all-targets
real 5.63   user 9.34   sys 2.11
```

5.6 s on a warm cargo registry (was 4.9 s with three fewer crates in the
workspace). Still the floor, not a property.

## (b) `cargo reconverge check --strict` on an exercise kernel (tier 0)

Kernel: `exercises/b1-first-kernel` (elementwise skeleton, cuda-device
`a766fc26`, pinned nightly via the exercise's `rust-toolchain.toml`).

```
$ cd exercises/b1-first-kernel
$ cargo clean && /usr/bin/time -p cargo reconverge check --strict   # cold
reconverge: 0 deny, 0 confirmed, 0 warning finding(s)
real 4.16
$ /usr/bin/time -p cargo reconverge check --strict                  # warm
real 0.08
```

Cold ≈ 4.2 s (was 3.6 s under 0.2.0 — the analyzer grew), warm ≈ 0.08 s,
unchanged. The gate stays effectively free after the first build.

## (c) `cargo oxide inspect` in the tier-1 container

Container: Apple `container` tool, native arm64 Ubuntu 24.04 guest,
CUDA toolkit 13.2 (sbsa), LLVM 21, pinned nightly, cargo-oxide 0.2.1 —
all unchanged by this bump (cuda-oxide and the nightly did not move).

```
$ container exec cuda-oxide-dev bash -lc 'cd /work && time cargo oxide inspect vecadd'
real 0m2.097s    # warm target cache; 9.4 s on the first run after provisioning
```

Real PTX (`add.f32`, `st.global.b32`) as before. The standing finding
holds: a `#[kernel]` whose body is `todo!()` builds but emits no PTX, so
the inspect step gates the solution, not the skeleton. The
arm64-container-vs-x86-box byte-identity check is still owed at exercise
D1.

## (d) launchbound 1.2.0 driving reconverge 0.3.0 — the pin pairing

launchbound 1.2.0 pins reconverge 0.3.0 internally, so for the first time
this project's pairing and launchbound's own are identical. Upstream's
release measurement compared analyzer verdicts 0.1.11 vs 0.3.0 over its
corpus byte-identically (93 clean, 8 refused, same hashes); this is our
independent check on this machine.

Clean space (this repo's B1 skeleton, 3 configs):

```
$ cd exercises/b1-first-kernel && launchbound prune --cc 7.5 .
b1-first-kernel (cc 7.5):
  => 3 clean, 0 with caveats, 0 refused, 0 tool errors
real 3.10
```

Refusal flow (the known-flip corpus kernel from
`vyncint/launchbound-action-demo`, 4 configs, cc 8.6):

```
block_x=32 tile=128 -> clean []
block_x=32 tile=256 -> clean []
block_x=64 tile=128 -> disqualified ['RC001']
block_x=64 tile=256 -> disqualified ['RC001']
```

Identical verdicts to the 0.2.0/1.0.2 baseline, in both directions. The
B2/B3 skeletons also re-gate clean (`0 deny, 0 confirmed, 0 warning`),
and B3's two-tile space stays 2-clean at both `--cc` values while its
body is `todo!()`. **Verdict: launchbound 1.2.0 drives reconverge 0.3.0
correctly; no fallback needed.**

## Non-transfer reminders

A verdict is per-`--cc` (RC004 shared-memory context differs between 7.5
and 8.6) and timings are per-part. Nothing in this file predicts NVIDIA
performance; it measures tool latency on one laptop.
